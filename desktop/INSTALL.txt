Freebuff AdBlock for Desktop  (v__FBD_VERSION__)
=================================================

Blocks the ads Freebuff Desktop renders from the orchestrator it ships inside
its own app bundle.

WHAT IS IN THIS FOLDER
----------------------

  Freebuff AdBlock.command   Double-click this. It opens Terminal and patches
                             the app.

  freebuff-adblock.sh        The tool itself, if you would rather run it by hand:

                               sh freebuff-adblock.sh install

USING IT
--------

1. Freebuff Desktop must be installed (usually /Applications/Freebuff.app).

2. Double-click "Freebuff AdBlock.command", or run:

     sh freebuff-adblock.sh install

3. Quit Freebuff completely (Cmd-Q) and reopen it. The orchestrator is read
   once at launch, so the patch only takes effect on the next start - focusing
   the window is not enough. The tool waits for that relaunch and then reports
   what the app it finds is actually running, so the patch does not have to be
   taken on trust. Ctrl-C stops the wait at any time.

macOS may ask you for permission the first time, because this writes inside an
app bundle. If you see "Operation not permitted", open:

  System Settings -> Privacy & Security -> App Management

switch on Terminal (or whichever app you ran this from), quit and reopen that
app, and run the tool again. It never asks for a password and never uses sudo.

OTHER COMMANDS
--------------

  sh freebuff-adblock.sh status    report what is applied - changes nothing
  sh freebuff-adblock.sh verify    wait for the relaunch, then check what it loaded
  sh freebuff-adblock.sh scan      show every anchor this build has - changes nothing
  sh freebuff-adblock.sh revert    restore the untouched original
  sh freebuff-adblock.sh doctor    environment report, for a bug report

AFTER A FREEBUFF UPDATE
-----------------------

Every update replaces the app's Resources folder, so the patch goes away. Run
install again after an update.

An update can also change the code the tool looks for. Each anchor has a
literal form and a relaxed one; the relaxed form is only used when it appears
the expected number of times AND ad code sits beside it, and the write is
undone if the check afterwards disagrees. When an anchor does not fit, install
refuses and prints the counts it saw - "render ambiguous, literal: 2 match(es)"
- so you can see whether the shape changed or only the number of times it
appears. To get the full report:

  sh freebuff-adblock.sh scan                     (a local copy of the tool)

  curl -fsSL __FBD_ORIGIN__/downloads/freebuff-adblock-desktop.sh | sh -s scan

Both list every candidate site the build has, write a copy to your backup
folder, and touch nothing inside the app. The piped one is for when you ran the
one-liner above and have no local copy to point at.

IS IT ACTUALLY OFF?
--------------------

A patch on disk is not a patch in effect. The orchestrator is read once, when
Freebuff starts, so patching a running app changes nothing until it is
relaunched. That is what `verify` is for:

  sh freebuff-adblock.sh verify

It waits for Freebuff to be quit and reopened, then compares two times - when the
patch was written, and when the process running now started. Started later means
the app you are looking at is the one that read the patched file. It also lists
the ad code still in the build, so you can see the patch is aimed at something
real rather than at code that has moved. `install` runs the same check for you
whenever Freebuff is open, which is why it sits and waits after patching.

  sh freebuff-adblock.sh verify --no-wait       report now, do not wait
  sh freebuff-adblock.sh verify --timeout 60    wait at most a minute

The one thing none of this can see is whether an ad break still appears - that is
the app's behaviour, and only you can watch it. On the free tier, run a turn and
watch the thread: an ad card is the one carrying an "AD" chip or a /track/click
link. If one appears with both markers applied and the process started after the
patch, that is worth reporting - it means Freebuff has a second ad path, and the
scan report above is what a re-anchor needs.

WHAT IT DOES
------------

It only touches the ad code in
Contents/Resources/orchestrator/orchestrator.js. It forces the gate the ad
auction consults to return "no ads to show", and makes the ad client's own
request helper fail before it sends, so none of the /api/v1/ads/* calls can be
reached. Nothing else changes - in particular the log shipper that posts to
/api/logs is left alone.

It refuses to run unless every anchor it expects is found the exact number of
times it expects, so a Freebuff version that renames something fails safe and
changes nothing rather than half-patching a 9 MB file. A relaxed match is
accepted only when ad code sits beside it, so a similarly shaped gate elsewhere
in the bundle is never mistaken for the ad render path. The untouched original
is backed up before the first write, and `revert` puts it back.
