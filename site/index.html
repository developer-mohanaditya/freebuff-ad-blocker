How it works

Three layers, in the order they fire

01

Network rules

A declarativeNetRequest ruleset blocks known ad and tracker hosts before the request leaves the tab. Every rule is scoped to requests initiated by freebuff.com, so it never follows you to other sites.

02

Mid-build cleanup

Slots rendered client-side never make a separate ad request, so a blocklist cannot see them. A content script watches the DOM and removes the ones inserted while the platform is thinking, then collapses the empty space they leave behind.

The same layer covers freebuff.com's own in-product promo cards — the ones with a literal AD chip next to CodeRabbit or Baseten. Those are first-party, so only reading the page can remove them. They are matched on the badge text and never on page text alone, and nothing holding a link-free paragraph, a code block or an editor is ever touched.

03

One switch

The toolbar popup pauses blocking for the whole site in one click and shows what was hidden on the current tab. The setting syncs through chrome.storage — no account, no dashboard.

It also carries the escape hatch: Hide an element on the page. Click it, click an ad nothing recognised, and the rule sticks on every future visit. That is the part no heuristic can replace — a blocker only finds what it was taught, and the picker is how you teach it.

The part that matters

It cannot break your build stream

Your build and thinking progress arrives over XHR and WebSocket from freebuff.com itself. A single mis-scoped rule would cut that off. So the ruleset carries a priority-100 allow rule for freebuff.com's own traffic that every block rule — all priority 1 — has to lose against. Path-based rules are slash-anchored so /load and /headers can never match, and the content script refuses to hide any element that still holds real content.

id 1 priority 100 allow freebuff.com
id 10 priority 1 block doubleclick.net
id 12 priority 1 block adnxs.com

Install

Load it unpacked — about a minute

Neither Chromium nor Firefox will install an unsigned extension from a link, so until a store listing is live the path is loading the extracted folder as a developer extension. It behaves exactly like an installed one — in Chromium it persists, in Firefox a temporary add-on lasts until the browser restarts.

  1. 1

    Download and extract

    Grab the zip and unpack it somewhere permanent. If you move the folder later, Chrome will report the extension as unloaded and you will need to point it at the new path again.

    Download extension v1.6.0 · zip

    /downloads/freebuff-adblock-1.6.0.zip
  2. 2

    Open the extensions page

    Visit chrome://extensions — or edge://extensions / brave://extensions — and switch on Developer mode in the top right corner.

  3. 3

    Choose Load unpacked

    Press Load unpacked and select the extracted freebuff-adblock folder — the one containing manifest.json. The toolbar icon appears and you are done.

  4. 4

    Reload your open freebuff.com tabs

    Content scripts only attach to pages loaded after the extension is enabled. Reload any tab that was already open, then check the popup — the hidden-element counter starts climbing.

Firefox

Firefox has no Manifest V3 service worker, so it runs the background as an event page. That key is Manifest V2 as far as Chromium is concerned: ignored, but reported as a warning on the extensions page. Rather than make every package carry it, the build writes a Firefox variant with the key added. Everything else is shared — the same ruleset, the same content script, the same popup.

Download the Firefox package, then open about:debugging#/runtime/this-firefox, choose Load Temporary Add-on, and select manifest.json from the folder you extracted. A temporary add-on lasts until Firefox restarts — a build signed on addons.mozilla.org is the persistent route.

What a listing changes

A store listing removes every step above: one click, and the store handles updates. It is also the only route that survives a restart without reloading anything by hand.

Two packages are built for submission, both with manifest.json at the archive root, which is what the stores require: one for the Chrome Web Store and Edge Add-ons, and one for addons.mozilla.org.

Safari is the exception. It needs a separate build wrapped in a native app and a paid Apple developer account, so browsers that detect as Safari get no button at all — better a missing button than one that leads nowhere.

Auto-updates

What the update feed does, and does not, do

Unpacked extensions do not auto-update

This is the honest part. Chrome only checks an update.xml feed for extensions that were installed from that feed. A folder you loaded unpacked is treated as local source: Chrome will never poll for a newer version of it, and none of the files on this site can change that.

To update, download the new zip, extract it, and hit the refresh button on the extension card in chrome://extensions.

The feed is built and ready

The build regenerates update.xml alongside every package, with the matching version and codebase URL. Wire it up when you want automatic updates, by either route:

  • Managed policy — set ExtensionInstallForcelist on your own machine, pointing at the feed. Chrome then installs, updates and reloads it for you.
  • Chrome Web Store — publish it and the store handles distribution and rollouts entirely.

Both require the placeholder app ID in update.xml to be replaced with the packed extension's real ID, and a signed CRX rather than a zip.

Desktop app

The desktop app, blocked the same way

Freebuff Desktop is a separate app that renders its ads from a runtime inside its own bundle — there is no extension surface, so a browser extension can never reach it. This is the other half: a small local tool that turns that ad runtime off in place. It runs entirely on your machine, needs no account, and sends nothing anywhere.

All three have a tool. Pick your platform — the switch opens on the one you are reading this on, and each tab's download is that platform's build.

Run it

One line, and nothing to install first — macOS already ships the sh and perl it uses. The tool writes a copy of the original file before it touches anything, and revert puts it back.

curl -fsSL https://freebuff-adblocker.vercel.app/downloads/freebuff-adblock-desktop.sh | sh

Prefer a file? Download the tool — a zip with a double-clickable launcher and a short read-me — then run sh freebuff-adblock.sh install.

Report what is applied, and change nothing: sh freebuff-adblock.sh status. Check what the app you have open actually loaded — it waits for the relaunch and then says so: sh freebuff-adblock.sh verify. Undo it: sh freebuff-adblock.sh revert.

Tool v1.6.0, anchored against Freebuff Desktop 0.0.164: it forces the ad auction to return nothing and cuts the ad client off from its API, and it undoes its own write if the result does not check out. If a Freebuff release moves something it cannot recognise, it refuses and prints the counts it saw instead of guessing — and sh freebuff-adblock.sh scan prints what the installed build actually contains, changing nothing. An older Freebuff with a different arrangement is refused, not half-patched.

After you run it

  1. Quit Freebuff completely (⌘Q) and reopen it. The orchestrator is read once at launch, so bringing the window forward is not enough. The tool waits for that relaunch and then reports what it finds: whether the running process started after the patch was written, and whether the ad code it targets is still in the build. Ctrl-C stops the wait.
  2. If macOS says “Operation not permitted”, it is App Management holding the write back. Open System Settings → Privacy & Security → App Management, switch on Terminal (or whichever app you ran it from), quit and reopen that app, and run it again. The tool never asks for a password and never uses sudo.
  3. After a Freebuff update, run it again. An update replaces the app's Resources folder, so the patch goes with it. The backup is kept for each version, so reverting an older one still works.

Run it

One line in PowerShell, and nothing to install first — Windows ships PowerShell, irm and iex with the OS. Piping straight into iex is also the easier way in: no file is written to disk, so Windows never tags it as a download, and the execution policy — which governs .ps1 files — never comes into it. The tool writes a copy of the original file before it touches anything, and revert puts it back.

irm https://freebuff-adblocker.vercel.app/downloads/freebuff-adblock-desktop.ps1 | iex

Prefer a file? Download the tool — a zip with a double-clickable launcher and a short read-me. A saved file carries the mark-of-the-web, so either unblock it first with Unblock-File .\freebuff-adblock-desktop.ps1, or run it the way the launcher does: powershell -ExecutionPolicy Bypass -File .\freebuff-adblock-desktop.ps1 install.

The other commands need the scriptblock form, because iex takes a string and nothing else: $s = irm …/downloads/freebuff-adblock-desktop.ps1; & ([scriptblock]::Create($s)) status. status reports what is applied and changes nothing, verify waits for the relaunch and then says what the app you have open actually loaded, scan prints every anchor this build has, and revert restores the untouched original.

Tool v1.6.0, anchored against Freebuff Desktop 0.0.164 — the same two anchors as the macOS tool: it forces the ad auction to return nothing and cuts the ad client off from its API, and it undoes its own write if the result does not check out. It finds the install itself (the per-user folder under %LOCALAPPDATA%\Programs, Program Files, Squirrel's app-<version> folders, and the uninstall registry entries), and -App points it somewhere else if your copy lives off the beaten path. If a Freebuff release moves something it cannot recognise, it refuses and prints the counts it saw instead of guessing — and … ([scriptblock]::Create($s)) scan prints what the installed build actually contains, changing nothing.

After you run it

  1. Quit Freebuff completely and reopen it — from the tray icon, or by ending Freebuff.exe in Task Manager. The orchestrator is read once at launch, so bringing the window forward is not enough. The tool waits for that relaunch and then reports what it finds: whether the running process started after the patch was written, and whether the ad code it targets is still in the build. Ctrl-C stops the wait; an interrupted wait prints no verdict.
  2. If it says Freebuff has the file open, that is Windows refusing to replace a file another process is holding — quit Freebuff properly (closing the window is not always quitting) and run it again. The tool will not force the write.
  3. If the write is refused on a machine-wide install (under C:\Program Files), open PowerShell with Run as administrator and run the same command. A per-user install under %LOCALAPPDATA%\Programs never needs that, and the tool never asks for a password or elevates by itself.
  4. After a Freebuff update, run it again. An update replaces the app's resources folder, so the patch goes with it. The backup is kept per version, so reverting an older one still works.

Run it

One line, and nothing to install first — it is a shell script using the perl and pgrep your distribution already has. Freebuff for Linux ships as an AppImage: one executable holding a read-only filesystem, so there is no file inside it to patch. The tool never writes to your download. It extracts the image with the runtime the image itself carries — no FUSE, no squashfs-tools, no root — patches that copy, and tells you to start it instead.

curl -fsSL https://freebuff-adblocker.vercel.app/downloads/freebuff-adblock-desktop-linux.sh | sh

Prefer a file? Download the tool — a zip with the script and a short read-me — then run sh freebuff-adblock-linux.sh.

Report what is applied, and change nothing: sh freebuff-adblock-linux.sh status. Check what the copy you started actually loaded — it waits for the relaunch and then says so: sh freebuff-adblock-linux.sh verify. Undo it: sh freebuff-adblock-linux.sh revert. Pointed at a directory instead — an AppDir you extracted yourself — it patches in place, exactly like the macOS tool.

Tool v1.6.0, anchored against Freebuff Desktop 0.0.164 — the same two anchors, verified against the real Linux build: it forces the ad auction to return nothing and cuts the ad client off from its API, and it undoes its own write if the result does not check out. It looks for *Freebuff*.AppImage in ~/Applications, ~/Downloads, ~/.local/bin, /opt and elsewhere, and --app points it at the image or directory you mean. If a Freebuff release moves something it cannot recognise, it refuses and prints the counts it saw instead of guessing — and scan prints what that build actually contains, changing nothing.

After you run it

  1. Start the patched copy, not the image. The path is printed for you, and it is under ~/.local/share/freebuff-adblock. The orchestrator is read once at launch, so the patch only takes effect on the next start. Your original .AppImage is untouched — keep it as the unpatched fallback, because running it still shows ads.
  2. Then check what it loaded: sh freebuff-adblock-linux.sh verify. It waits for something to be running the patched file, then compares when the patch was written against when that process started. Ctrl-C stops the wait; an interrupted wait prints no verdict.
  3. If the directory is not writable, you are pointing at a system-wide install under /opt or /usr, which belongs to root. Use the AppImage path instead — that never needs it — or re-run the same command with sudo if you really mean to patch the system copy. The tool never escalates by itself and never asks for a password.
  4. After a Freebuff update, run it again. An update is a new AppImage, so the patched copy is left behind by it. Each version is extracted into its own directory, so nothing is overwritten and the backup is kept per version.

Why it is safe to run

It refuses to guess

The tool matches the exact ad code it expects to find, and only the ad code: the one gate the ad auction consults, and the one request helper every ad API call goes through. It counts every anchor before it writes, and if the numbers do not match — a new Freebuff version that renamed something, or a file someone already edited — it stops and changes nothing, rather than half-patching a 9 MB file. Every run prints what it found first, so status tells you exactly what is applied on your machine.

render 1 anchor off the auction gate
request 1 anchor off ad request helper
Scope

Two apps, one idea, and a tool for each — because neither can reach the other. The web version is covered by the extension above, which a browser can only reach because Chromium renders the page. The desktop app is a separate bundle with no extension surface, so it is covered by the local tool in For Desktop instead: one build per platform, macOS, Windows and Linux. Neither has a server, an account or a telemetry endpoint, and neither touches anything outside freebuff.com and your own machine.
